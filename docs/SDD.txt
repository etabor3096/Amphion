1 Problem & Users
1.1 Problem Description
Most people learn guitar by playing songs they already love, but beginners hit a wall: they
do not yet have the ear training to work out a song by listening. Figuring out which notes
or chords are being played, where they sit on the fretboard, and when the changes
happen is a skill that takes years to develop. Until then, a beginner depends on someone
else having written the song down as tablature (tabs), a simple notation that shows which
string and fret to play.
That dependency breaks down often. Many songs have no tabs at all, including newer
releases, songs by smaller or local artists, live arrangements, and church worship sets.
When tabs do exist, they are usually written by volunteers and are frequently wrong:
incorrect notes or chords, the wrong tuning or capo position, or timing that does not
match the recording. An experienced player can spot and fix these mistakes by ear. A
beginner cannot, so they practice the wrong part, cannot make it sound like the record,
and often conclude the problem is their own ability.
The core problem is that beginner and early-intermediate guitar and bass players have no
reliable way to turn a song they hear into an accurate, playable part when good tabs are
missing or wrong, and they lack the ear skills to do it themselves.

2 Proposed Solution & Scope
2.1 Proposed Solution
Amphion is an iOS app that listens to a song and turns it into guitar or bass tablature (tab)
that a beginner can play along with. A user either records audio through the phone's
microphone (a song playing nearby, or themselves playing) or uploads an audio file they
own. Amphion separates the guitar and bass parts from the rest of the mix, analyzes
them, and produces a tab: which string and fret to play for each note, lined up with the
song's beats and bars. Chord names appear in a small line above the tab as a supporting
guide.
The user then practices inside the app. When they press play, the song plays and the tab
moves with it: a playhead sweeps across the tab, the notes being played light up, and the
tab scrolls on its own so the current bar is always on screen. The user can slow the song
down, loop a hard section, or tap any note to jump there, and the tab stays locked to the
audio the whole time. Amphion also reports the song's key, tempo, and tuning so the user
is set up correctly before they start. Where the analysis is unsure, Amphion says so
instead of hiding it: low-confidence notes are flagged, and the user can correct them.
Every transcription is saved to the user's personal library.
The expected value is that a beginner no longer depends on someone else having written
an accurate tab. Any song they can play or record becomes something they can learn, and
the honest confidence flags keep them from practicing mistakes without knowing it. A
guitar teacher gets the same benefit as a fast first draft to check before a lesson.

2.2 Minimum Viable Product (MVP) Scope
The MVP proves one thing: Amphion can turn a recorded or uploaded song into beat-
synced guitar or bass tablature that plays in sync with the song, so a beginner can
practice with it. It includes:
Audio input: record from the microphone or upload an audio file from the device.
Tab transcription: separate the guitar and bass parts from the mix, detect the notes in
each part, give every note a playable string and fret, and line notes up with the
detected beat grid. Chord names are detected as a secondary layer shown above the
tab.
Song details: detect and display key, tempo (BPM), and tuning (how far the recording
sits from standard pitch).
Synced tab playback: the song plays with a moving playhead, highlighted current
notes, and automatic scrolling, all driven by the audio's own playback position so the
tab never drifts from the song; plus tap-to-jump, slow-down, and A-B looping
(repeating a chosen section).
Confidence flags and editing: low-confidence notes are visibly marked, and the user
can change, add, or delete any note.
Accounts and personal library: sign up, sign in, reset a forgotten password, manage
the account (display name, email, password, account deletion), and save, reopen,
rename, and delete transcriptions, organize them into folders, give each song its own
artwork, and search, filter, and sort the library.
Supporting capability: a processing service that runs the analysis without the user
keeping the app open on one screen, and cloud storage for accounts and saved
transcription results (song audio stays on the phone; see RC-03).
The MVP accepts songs up to 3 minutes long (RC-07); supporting full-length songs is a
goal by the end of the project (OQ-04).
2.3 Out of Scope / Non-Goals
Not part of this project:
Real-time transcription. Results appear after processing finishes, not live while the
song plays.
Sharing or a public tab library. Transcriptions stay private to the user who made them;
there is no posting, publishing, or exchanging tabs between users.

US-07 - View Beat-Synced Tablature
User Story: As a player, I can see the song as tablature laid out on its beats and bars so

User Story: As a player of acoustic guitar, electric guitar, or bass, I can switch between a

User Story: As a player, I can see the song's key, tempo, and tuning so that I can set up my

4 Requirements, Constraints & Design Rules
These rules apply across all user stories and must be respected by every future
implementer, human or AI.
Security & Privacy
RC-01 - Authentication: All functionality except the sign-in screens requires a signed-in
account. Supported methods are Sign in with Apple, Google sign-in, and email/password.
The backend must verify the user's identity on every request rather than trusting the app.
RC-02 - Per-User Data Isolation: A user can read, edit, or delete only their own
transcriptions and account data. No request may return or change another user's data.
RC-03 - Audio Retention: Song audio is uploaded only for processing and must be deleted
from cloud storage as soon as the processing job finishes or fails. The separated guitar
and bass parts made from it exist only inside the running job and are never stored. The
cloud keeps only the transcription results (notes with their string and fret, beats, chord
names, song details, edits) and any custom song artwork (DD-13). The phone keeps its
local copy of the audio for playback.
RC-04 - Private by Design: Transcriptions are private to their owner. The MVP must not
include any feature that publishes, shares, or exports transcriptions or audio to other
users.
RC-05 - Microphone Use: The app records only after the user taps Record and stops
when the user taps Stop or the length limit is reached. There is no background or always-
on listening. The microphone permission prompt must explain why access is needed.
RC-06 - Secrets & Credentials: API keys, service credentials, and other secrets must
never be embedded in the iOS app or committed to the repository.
RC-15 - Account Deletion: Users must be able to delete their account from inside the app
(Settings > Account), as Apple requires for any app that supports account creation.
Deletion requires confirmation and recent sign-in, removes the user's authentication

Performance & Reliability
RC-07 - Input Limits: The MVP accepts MP3, M4A, and WAV audio up to 3 minutes long.
Limits are checked in the app before upload and enforced again by the backend.
RC-08 - Processing Time: Under normal network conditions, a 3-minute song must finish
processing in under 2 minutes from upload to Ready.
RC-09 - Failure Handling: A failed or timed-out job must show a Failed state with a retry
option. The app must never show a partial or empty tab as if it were complete.
RC-10 - Accuracy Benchmark: The project keeps a reference set of at least 10 songs with
hand-checked guitar tabs (and bass tabs where the song has a bass part), covering both
uploaded files and phone-mic recordings. Note accuracy is measured against this set
whenever the transcription pipeline changes, so improvements and regressions are
visible. A detected note counts as correct when its pitch matches a reference note and it
starts within 50 ms of it; string and fret choices are scored separately. Chord-name
accuracy is still measured for the fallback (RISK-01). The pass thresholds are tracked in
Section 7.2.
RC-18 - One Clock for Sync: Every note, beat, bar, and chord time is stored in seconds
from the start of the song's audio file (song time). During playback, the Song screen reads
the current song time from the audio player itself on every screen refresh and draws the
playhead and highlights from it; it never runs its own timer. Speed changes and loops
change only how fast song time moves, so the stored tab never has to change. The display
corrects for the device's audio output delay (for example, Bluetooth headphones) so the
highlighted note matches what the user hears.

RC-19 - Same Audio for Analysis and Playback: The app uploads exactly the audio file it
keeps on the phone for playback, with no trimming or re-encoding after upload, so the
times the pipeline produces line up with the local file. The song record stores the file's
duration and a content fingerprint (hash). If the local file is missing or does not match, the
Song screen shows the tab without synced playback (OQ-03) rather than playing out of
sync.
RC-20 - Tab Data Format: For each instrument, the pipeline stores a list of notes with start
time, length, string, fret, pitch (MIDI note number), confidence, and whether the user
edited it, plus the beat and downbeat times and the chord-name segments. Results are
written to Firestore in chunks by bar range so no single record approaches Firestore's 1
MB document limit as songs grow toward full length (OQ-04).
Accessibility & User Experience
RC-11 - Honest Output: Amphion must never present uncertain results as certain. Notes
and chord names below the confidence threshold are always marked, and any song detail
that could not be determined is shown as "Unknown" rather than guessed.
RC-12 - Accessibility: All controls have VoiceOver labels, text respects Dynamic Type
sizes, confidence markers and the current-note highlight do not rely on color alone, the
tab can be read by VoiceOver bar by bar (for example,
"Bar 3, beat 1: A string, fret 2"), and
each chord diagram has a text alternative (for example,
"G major, open position").
RC-13 - Beginner-Friendly Language: User-facing text uses plain musical terms a beginner
can follow and briefly explains terms such as tab, BPM, and tuning offset where they
appear. Machine-learning or internal technical terms are never shown to users.
Platform & Compatibility
RC-14 - Supported Devices: The MVP targets iPhone on iOS 17 or later. iPad layouts,
Android, web, and desktop are not required.

5.2 Architecture Diagram & Explanation
The app never talks to the processing service directly. It uploads audio to Cloud Storage
and creates a song record in Firestore with status Processing. The upload triggers the
processing function, which downloads the audio, separates the guitar and bass parts,
detects notes and assigns strings and frets, runs the beat, chord, key, tempo, and tuning
analysis, writes the tab and song details to Firestore, sets the status to Ready (or Failed),
deletes the audio from storage, and sends a push notification. Because the app listens to
its Firestore records, the library updates as soon as the status changes. During playback
the app needs nothing from the cloud: it plays its local audio file and draws the tab from
the saved results (RC-18, RC-19).
This design keeps all credentials and the ML code in the cloud (RC-06), keeps only results
in the cloud (RC-03), and lets the analysis pipeline change without an app update.

artist (US-16, US-17).

DD-02 - Pretrained Models Instead of Training a Custom Model: The pipeline uses
existing open-source pretrained models (Demucs, Basic Pitch, madmom, librosa) rather
than collecting data and training a new model. This keeps the ML risk inside a solo
semester project and lets effort go into the user experience, the tab-assignment rules,
and accuracy measurement (RC-10).
DD-03 - Cloud Processing with Temporary Audio: All analysis runs in the cloud, not on the
phone. Audio is uploaded only for processing and deleted when the job ends (RC-03). This
resolves the earlier open choice between on-device and cloud processing: cloud
processing allows heavier models and pipeline updates without an app release, and
deleting audio limits storage cost and copyright exposure.
DD-04 - Native SwiftUI Client: The app is built in SwiftUI rather than a cross-platform
framework because the project is iOS-first and the core practice features (pitch-
preserving slow-down, looping, recording) depend on Apple's AVFoundation audio
framework. A future Android app would need a new client UI, but the backend and
processing pipeline are platform-neutral and would be reused unchanged.
DD-05 - Upload-Triggered Pipeline: The app never calls the processing service directly.
Uploading audio to Cloud Storage triggers processing, and results flow back through
Firestore, which the app already listens to. This keeps credentials and ML code off the
device (RC-06) and makes job status simple to show (US-06).
DD-06 - Show Uncertainty Instead of Hiding It: Low-confidence notes and chord names
are flagged and editable (US-10, US-11, RC-11). Beginners cannot judge accuracy by ear, so
the app must tell them where to double-check rather than present every result as
correct.
DD-07 - Private-Only Library: Transcriptions are visible only to their owner and cannot be
shared (RC-04). This keeps the MVP focused and avoids redistributing copyrighted
material.
DD-08 - Capo Deferred, Tuning Reported as an Offset: Audio alone cannot show whether
a capo was used, so capo suggestions are deferred (Section 2.3). Tuning is reported as
how far the recording sits from standard pitch rather than as a named tuning.

DD-09 - Display Name Instead of Username: The account has an editable display name
used only in the app's own greetings, and no username. Because the library is private-only
(RC-04), no other user ever sees a name, so unique usernames would add uniqueness
checks and taken-name handling with no user benefit.
DD-10 - Provider-Managed Credentials: Users who sign in with Apple or Google have no
Amphion password; their email and password are managed by that provider. Only
email/password accounts can change their password or email in the app, and those
changes require re-entering the current password first.
DD-11 - One Folder per Song: Each song sits in at most one folder, like a file on a computer,
rather than in several playlists at once. This keeps moving and deleting simple for
beginners and keeps the data model to a single folder field per song. Multi-folder playlists
could be added later without changing existing data.
DD-12 - Artist Entered by the User: Amphion does not identify songs or artists
automatically. Song recognition would need a third-party audio-fingerprinting service
with its own cost and licensing terms, and many target songs (original, local, or live
recordings) would not be recognized anyway. Artist is an optional text field the user fills in
on the review step or later, and it powers the artist search, filter, and sort (US-17).
DD-13 - Artwork Stored in the Cloud, Audio Is Not: Unlike song audio (RC-03), custom
artwork is kept in Cloud Storage so it appears on every iPhone the user signs in on.
Artwork is the user's own photo, small after compression, and carries none of the
copyright concerns of song audio, so keeping it does not conflict with the audio-retention
rule. Songs without custom artwork use generated abstract art, so the Library never
shows blank cards.
DD-14 - The Audio Player Is the Only Clock: Synced playback reads the song position
from the audio player on every screen refresh instead of starting a separate timer when
play is pressed. A separate timer drifts, and it breaks as soon as the user pauses, scrubs,
slows down, or loops. Because all tab data is stored in song time (RC-18), the same tab
works unchanged at every speed and across every loop.
DD-15 - Beginner-Friendly String and Fret Choices: A detected pitch can usually be
played in several places on the neck. The tab-assignment step scores each option,
preferring open strings and lower frets, keeping notes that sound together within a
reachable span, and avoiding big hand jumps between neighboring notes, then picks the
best-scoring path through the whole song. These preferences are written as named,
adjustable weights so they can be tuned against the benchmark (RC-10). This is not the
deferred simplified-fingering feature: every detected note is still shown.

DD-16 - Separate Guitar and Bass Before Detecting Notes: Stem separation moves from
stretch goal into the MVP pipeline. Note detection on a full mix picks up vocals, keys, and
drums as false guitar notes, so the processing service first separates the guitar and bass
parts and detects notes in each part on its own. The separated parts exist only inside the
running job and are never stored (RC-03). The costs are extra processing time (RISK-02)
and a single combined guitar tab when a song has more than one guitar part (RISK-06).

RISK-01 - Tab Accuracy (go/no-go
checkpoint)
Note detection on separated parts may be
much less accurate on full-mix recordings and

Checkpoint: 4 weeks after implementation
starts, measure note accuracy on the 10-song

score that rewards finding the reference notes
and penalizes extra wrong notes. The proposed
pass bar is 60% for guitar on uploaded files
(OQ-07). Fallback if missed: make the beat-
synced chord chart the main view again,
keeping the same synced playback, playhead,
and practice controls, and return note-level
tabs to stretch-goal status. If chord accuracy

chord identifier. A future agent must not
silently lower either bar or switch to a fallback
without this measurement.
RISK-02 - Processing Time and Cost Stem separation and note detection add real
work to the pipeline and may push a 3-minute
song past the 2-minute target (RC-08),
especially on CPU-only processing. Measure
early; options include more memory per job, a
GPU-backed service, or relaxing RC-08, with
cost checked before switching.
